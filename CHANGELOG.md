# Changelog

## 1.4.0 - 2026-11-18

Changed (1.4.0-beta.5): one subscription type for every listener, the same on all five SDKs (Joryio BACKLOG D444 / D446, owner decisions 2026-11-23). `onCardsUpdated`, `onPlacementsUpdated` and `onFlagsUpdated` - on the instance and on the `Joryio` type - return an `io.joryio.sdk.JoryioSubscription` instead of a bare `Closeable`: `cancel()` stops the updates - the same type name and method on iOS, web, React Native and Unity (`JoryioSubscription.Cancel()`). It still implements `java.io.Closeable`, so `close()` does the same as `cancel()` and `use { }` works; cancelling twice is harmless. The `Joryio` type (Kotlin `Joryio.x()`, Java `Joryio.Companion.x()`) gains `onPlacementsUpdated` (registered once initialized; cancelling before then cancels the registration, like `onFlagsUpdated`). It also gains the whole card data API, as on iOS's `Joryio.shared`: `markCardViewed` / `markCardRead` / `markCardClicked` / `dismissCard` take a `Card` or its id, are held until `initialize()` as data calls and are dropped while opted out or denied; `getUnreadCardCount()` answers 0 before `initialize()`; plus `getCards(cursor, callback)` and `onCardsUpdated(listener)`. Before, the type had only `getCards(callback)` and `refreshCards()`. Compose `JoryioCardFeed()` takes `pinnedLabel`, `dismissLabel` and `unreadLabel`, like `CardFeedView` and the feeds on iOS, web and React Native. Neither placements, flags nor cards are in a final release (none of the three listeners exists in 1.3.3), so the breaking renames are made now. No wire changes.

Added: joryio-android-ui `PlacementView` and joryio-android-compose `JoryioPlacement` draw an item's recommended products (Joryio BACKLOG D444) - a horizontal row of product cards (image, title, price with the compare-at price struck through, optional button) below the item's content, or alone for a data item; colours from the app theme. A tap reports `clicked` with elementId `product:<id>` and opens the product link like a `deep_link` button, through `setLinkHandler` first (source `placement`). Options `showProducts` (default true), `productButtonText`, `productCardWidth` (dp), XML `app:joryioShowProducts`, `app:joryioProductButtonText`, `app:joryioProductCardWidth`. New `PLACEMENT_PRODUCT_ELEMENT_PREFIX`, `PLACEMENT_PRODUCT_CARD_WIDTH`, `placementProductElementId()`.

Added: the `time_on_screen` in-app trigger (Joryio BACKLOG D444 follow-up; the app equivalent of the web's `time_on_page`, contract `packages/backend/src/common/in-app-screen-triggers.ts`). A campaign shows once the person has been on a screen for `value` seconds - the screen named by the trigger's `screenName` (trimmed, case-insensitive) or any screen. The clock (`ScreenClock`) starts at `trackScreen` / a `Screen Viewed` event: a new name restarts it, the same name again does not, background time (ProcessLifecycleOwner ON_STOP to ON_START) does not count, and each campaign fires once per screen visit through the usual display gates. /sync now declares the `screen_context` capability (also when a host renderer draws), and the server sends such campaigns only to SDKs that declare it.

Added: one app-wide link handler, `Joryio.setLinkHandler { link -> ... }` / `clearLinkHandler()` (instance and static, safe before `initialize()`; `JoryioLinkHandler` is a fun interface), that receives EVERY link the SDK is about to open - an in-app message button or link, a `PlacementView` button or link, a card tap - http(s) and app deep links alike, as a `JoryioLink` (`url`, `source`: `JoryioLinkSource` with wire values `in_app` / `placement` / `card` / `push`, `campaignId`, `placementKey`, `itemId`, `cardId`, `isAppDeepLink`). Return true to take it over, false (or throw) for the behaviour without a handler; `link.openDefault()` runs that behaviour later (at most once, on the main thread). Refused schemes never reach the handler nor `startActivity`. Existing `onDeepLink` handlers keep receiving app deep links, after the app-wide handler declines. An in-app message's app deep link now reaches the handler; without one it is not opened, as before. Push links are not routed through it: the SDK never opens them on Android, your launcher activity receives `jry_deep_link` as before. No `forwardUniversalLinks` here: Android routes verified App Links to the app itself. The same names and source values on all five SDKs.

Added: content cards and the inbox (Joryio BACKLOG D444 Phase 3, docs/PLACEMENTS_PLAN.md section 11) - a persistent feed per person, filled from card campaigns and the journey step "Add card". joryio-android-ui: `CardFeedView` (a plain scrolling list: image, title, body, optional button, a "Pinned" marker, an unread dot and a dismiss control with an accessible label, "No messages yet" when empty - all overridable - in the app's theme); joryio-android-compose: `JoryioCardFeed()`. The view reports `viewed` then `read` once half a card was on screen for a second (the placement viewability rule, now one shared helper), `clicked` on a tap (then opens the url: http(s) in the browser, an app deep link through `onDeepLink`, refused schemes never) and `dismissed` on the x, and loads the next page near the end. Data first: `getCards(callback)` / `suspend getCards(cursor?)` returning `CardFeed { cards, unreadCount, nextCursor, stateScope }`, `getUnreadCardCount()` (from the cache), `markCardViewed` / `markCardRead` / `markCardClicked` / `dismissCard` (a `Card` or its id), `refreshCards()`, `onCardsUpdated(listener)` (returns a `JoryioSubscription`: `cancel()`, also a `Closeable`), all on the `Joryio` type too. One `POST v1/in-app/cards` per refresh (no retries), the feed cached in the SDK's storage per person for `CARD_FEED_TTL_SECONDS` (300), at most one request per `CARD_MIN_REFRESH_SECONDS` (30, extra calls coalesce), `notModified`, `success: false` and a 429 keep the cache; refreshed on foreground after the TTL, identity and consent changes and the silent push `jry_sync: "cards"`. Reports are `POST v1/in-app/track` with `{ deliveryToken, action, sessionId }`, each action once per card, applied to the cache at once. An anonymous visitor's read / dismissed ids (`stateScope: "device"`) are kept on the device and cleared on identify / reset / wipeData. Without tracking consent nothing is requested or reported. New sync capability `cards`. The same names and wire values on all five SDKs.

Added: placements (Joryio BACKLOG D444, docs/PLACEMENTS_PLAN.md) - named spots inside your app that Joryio fills per person from placement campaigns and journey steps. joryio-android-ui: `PlacementView` (XML `app:joryioPlacementKey="home_hero"` or `PlacementView(context, "home_hero")`); new artifact `io.joryio:joryio-android-compose` with `JoryioPlacement(placementKey)` for Jetpack Compose (a module of its own, so apps without Compose never pull it). Both draw native items as a card and HTML items (only delivered with `allowHtmlJsInAppMessages`) with no script, measure viewability (`PLACEMENT_VIEWABLE_FRACTION`, 0.5, for `IN_APP_DISPLAY_DWELL_MS` while the window has focus) and report impressions, clicks, dismissals and the holdout's `in_app.control_viewed`; content is never swapped while the view is on screen. Data first: `getPlacements(keys, callback)` and `suspend getPlacements(keys)`, `refreshPlacements(keys?)`, `onPlacementsUpdated(listener)` (returns a `JoryioSubscription`: `cancel()`, also a `Closeable`), `item.markDisplayed()` / `markClicked(elementId?)` / `markDismissed()`, `placement.markDisplayed()`. One `POST /v1/in-app/placements` per 50 ms batch (up to 10 keys, no retries), answers cached in the SDK's encrypted storage for `ttlSeconds` per person (wipeData clears them), at most one fetch per key per `PLACEMENT_MIN_REFRESH_SECONDS` (30), a 429 keeps the cache; refreshed on foreground after the TTL, identity and consent changes and the silent push `jry_sync: "placements"` (also `in_app`). Without tracking consent the request names nobody and nothing is reported. New sync capabilities `placements` and `content.data`. The same names and wire values on all five SDKs.

Added: feature flags and remote config (Joryio BACKLOG D446). `getFlag(key, defaultValue)` and the typed `getBoolFlag`, `getStringFlag`, `getNumberFlag` (`Double`), `getJsonFlag(key, defaultValue)` / `getJsonFlag(key, type, defaultValue)` (Gson) return the value Joryio decided for this person, or your in-code default before the first answer, for a flag Joryio did not send, for a value of another type, or without tracking consent; they never wait for the network. `getAllFlags()` (logs no exposure), `refreshFlags()` (suspend, and `refreshFlags(callback)`) and `onFlagsUpdated(listener)` (main thread, returns a `JoryioSubscription`: `cancel()`, also a `Closeable`). The same methods on `Joryio` itself for code that runs before `initialize()` finishes: the getters answer the default until then; `refreshFlags` and `onFlagsUpdated` are queued. Nothing is fetched until the app uses flags; then one `POST /v1/flags/evaluate` returns every flag, kept on the device for the same person only (`wipeData()` erases it) and refreshed at start, on foreground (at most once per `FLAGS_MIN_REFRESH_SECONDS`, 60), on identify / reset, on a consent change, on the silent push `jry_sync: "flags"` and on `refreshFlags()`, with the `etag` so an unchanged answer is not sent again. The first read of a value in a session logs an exposure (`POST /v1/flags/exposures`, batched, once per person, flag and variant per session, skipped when the answer says `logExposure: false`); each batch is sent as the person who read the values and dropped when consent is withdrawn first. The same names and wire values on all five SDKs.

Added: every request names the bridge too when there is one (BACKLOG D427). The SDK already sent `X-Joryio-SDK: android` and `X-Joryio-SDK-Version`; a React Native or Unity bridge now calls `Joryio.setSdkWrapper(name, version)` before `initialize()`, and its requests also carry `X-Joryio-SDK-Wrapper` (`react-native` / `unity`) and `X-Joryio-SDK-Wrapper-Version`. Settings > Apps shows the oldest version each app ran in the last 7 days and when a newer SDK is out. `setSdkWrapper` is for Joryio's own bridges; an app never calls it. The same wire names on all five SDKs.

Added: `resetTo(anonymousId)` (instance and `Joryio.resetTo`, held before `initialize()` like `reset()`) - everything `reset()` does, then the anonymous id you pass instead of a random one, for an app that keeps its own visitor id (BACKLOG D366). The id must be 8 to 255 letters, digits, `.`, `_`, `:` or `-`, must not have the shape of a Joryio profile id (24 lowercase hex) and must not be the user id the SDK holds; a refused id is logged and the call is a plain `reset()` (a random id), so a logout is never skipped. The same name and rule on all five SDKs. No wire changes: the server sees an ordinary anonymous id. Like `reset()`, `resetTo` drops a click-link token the SDK has not sent yet (one held while consent is pending), so the link is never attributed to the next person on the device.

Changed (BACKLOG D366, before any release of resetTo): it also refuses the anonymous id the SDK holds while a user is signed in - that id is tied to the signed-in person's profile, and adopting it would hand their in-app messages, events, form attribution and push subscription to the next person on a shared device (a random id is used instead). `resetTo` takes `onResult: ((Boolean) -> Unit)?`: `true` adopted, `false` refused; a call held before `initialize()` answers when it runs. The same on all five SDKs.

Changed (BACKLOG D366): `resetTo` also refuses the last 20 anonymous ids this device held for a signed-in user when a reset signed them out (stored locally, newest kept; `wipeData()` forgets them) - a random id is used and it answers `false`, the same message and cap on all five SDKs. A `resetTo` held before `initialize()` and discarded before it runs (a pre-`initialize()` `wipeData()`, or pushed out of a full buffer) now answers `false`, exactly once.

Added: `identifyFromLink(uri: Uri?)` and `identifyFromLink(url: String?)` (instance and `Joryio.identifyFromLink`, held before `initialize()` in memory like other data calls) - click-link identity. Pass the app link / deep link that opened the app (the Activity's `intent.data` in `onCreate` and `onNewIntent`); when it carries the `jr_t` token a tracked Joryio message link adds, the SDK sends it with the anonymous id to `POST v1/identify-link`. The server uses it only to attribute this app's session and later events (Session Start, screen views, conversions) to the contact the message was sent to - it never identifies the person: the app's profile does not become the contact and is never merged into it, and nothing set in the app is written to the contact. Only `identify` joins the two. Nothing happens when a user is identified, the person opted out or consent is denied; while consent is pending the token is held in memory and sent on `GRANTED`. The token is never persisted or logged above debug, and the same token is sent once per launch. The same name, parameter, path and body (`token`, `anonymousId`) on all five SDKs.

## 1.3.3 - 2026-11-03

Fixed: an in-app message counted as displayed the moment it was drawn, even when its screen closed straight away - a sign-in redirect, a logout. The person saw at most a flash, yet `in_app.displayed` was reported and the frequency cap was spent, so a capped campaign could be used up without ever being seen. A message the SDK draws now counts as displayed only after it has stayed on a resumed screen for `IN_APP_DISPLAY_DWELL_MS` (1000 ms, `io.joryio.sdk.messaging`); if the screen pauses the dwell stops, and it restarts in full on resume. A screen that finishes or is destroyed first reports nothing, spends nothing, and the message is offered on the next screen. Messages are drawn only on the resumed screen that is not finishing, destroyed or being recreated. A click or a dismissal before the dwell counts - `displayed` is reported first, then the interaction. A reset, identity change, opt-out or consent change before the dwell reports nothing. Presenters gain `InAppMessagePresenter.EVENT_HIDDEN` for a message removed without the person acting on it. Apps that draw messages themselves (`setInAppMessageCallback`) should report `displayed` by the same rule. Same name, value and rule on web, iOS, React Native and Unity; event names and properties are unchanged.

## 1.3.2 - 2026-10-25

Added: `JoryioConfig.holdInAppMessagesForHandler` (off by default). An app that draws in-app messages itself and calls `setInAppMessageCallback` after `initialize()` could have the first message drawn by the SDK: the sync `initialize()` starts could finish before the callback was set. With the option on, a message that is ready before the callback is held - not drawn, not reported, nothing spent - and handed to the callback when it is set; `clearInAppMessageCallback()` instead ends the hold and the SDK draws the held message. Reset, wipe and opt-out drop a held message. A held message is bound to the person it was chosen for: identify to another user, reset, wipe, opt-out and consent changes drop it, and delivery re-checks the anonymous id, user id and age (at most 5 minutes). The same option, by the same name, on iOS, React Native and Unity.

## 1.3.1 - 2026-10-24

Fixed: HTML in-app messages did not work on Android since 1.3.0. The script the SDK injects into the message page carried a link pattern with doubled backslashes, which the WebView rejected as a syntax error, so the whole bootstrap stopped: no `joryioBridge`, no height reporting, no button or link handling, no forms. The pattern is fixed and pinned by a test.

Fixed: an HTML modal or slide-up could grow but never shrink. The height is now measured from the message body, so a short message is as short as its content and a message re-fits when it gets shorter (a form replaced by its thank-you line). Heights stay capped at 90% of the screen; the message scrolls inside beyond that.

Added: `InAppCampaign.maxWidth` for HTML modals and slide-ups (dp - the same number as CSS pixels in the message, set by the "Max width" field in the dashboard; modal 600 and slide-up 400 when unset). With the `joryio-android-ui` artifact, the message is laid out at min(maxWidth, window width - margins) before its content loads, so the author's media queries see the real width; the slide-up sits at the bottom end with 12dp margins.
